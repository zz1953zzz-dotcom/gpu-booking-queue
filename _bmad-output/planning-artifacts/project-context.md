# 项目上下文 V1.0

第一版服务一个课题组。预配账号可具有组员、GPU 管理员或兼任角色。系统管理查卡、预约、排队、用卡、维护和异常协调。训练任务由组员在服务器上自行运行，系统依据登记资料、占用和交接状态判断可用性。浏览器前端通过接口访问 Django 后端。后端是模块化单体，共用 PostgreSQL。查询只读已提交状态，预约模块负责预约、队列、预留和用卡，维护模块通过预约模块的业务操作修改相关状态。

以 PRD 的功能需求、验收口径，架构 ADR-001 至 ADR-005 和故事验收条件为准。T1–T3 分别确定正式业务闭环、Windows 本机同源离线演示和 Django 数据库会话。P1–P3 分别确定共享接口与状态约定、演示就绪检查、故事证据与同版交付。DEC-027 至 DEC-033 记录用户决定。本轮技术工具及精确版本由用户授权代选，核对日期为 2026-11-15。以下文件名和命令名为后续实现约定，Windows 启动、断网复跑和业务验收均待实测。

## 十条工程约定

### 1. 前后端目录和产物归属

| 项 | 约定 |
| --- | --- |
| 适用场景 | 源码组织、静态构建、数据库迁移及交付 |
| 具体约定 | `frontend/src/` 管理 Vue 页面、组件和请求模块，`frontend/public/` 管理前端本地资源，`frontend/dist/` 为可重建发布产物。`backend/` 管理 Django 接口、业务服务、管理命令及数据库模型，各 Django app 的 `migrations/` 随后端源码提交。Caddy 通过演示目录提供前端产物。接口契约随代码版本交付。 |
| 依据 | DEC-027、DEC-029、DEC-031，ADR-001，故事 1.1、1.3、2.1 |
| 验证 | 从干净目录按锁文件重建前端，并在独立 PostgreSQL 上执行后端迁移。核对源码、产物和迁移追溯到同一版本。 |

### 2. 业务状态变更统一进入后端服务

| 项 | 约定 |
| --- | --- |
| 适用场景 | 预约、登记开始、取消、续用、领取、释放、匹配、到点处理和维护调整 |
| 具体约定 | 页面接口、扫描命令和维护处理调用同一业务服务。查询读取已提交状态。服务负责角色、归属、当前条件及事务内最终复检。提前预约由同卡统一受理入口按收到顺序逐笔持久化递增序号，同卡在先重叠申请结案前，后到申请等候。换卡同时锁定两张相关 GPU，按规则 3 加锁。领取与取消、登记开始与取消分别按首次成功确认结案。分配、有效预留、可见站内通知和待领取状态同事务提交。通知写入失败保持无已生效预留及原等待顺序和名额。结果不明先查原分配。领取截止前未收到有效请求，到期解除预留、结束该等待并释放名额。已收到有效请求满 30 秒仍未确认，解除预留、保序回队并保留名额。生效维护先结案时保留该结案和受影响状态，迟到结果和旧任务不得覆盖。调整及维护生效须取得当前版本所需逐人确认，再复检冲突和回避条件。挂起方案沿用原安排，旧版本确认不能授权新版。 |
| 依据 | ADR-001 至 ADR-005，FR-006、008 至 013、016 至 021、024 至 027，故事 2.2、2.4 至 2.8、3.2 至 3.5、4.2 至 4.5 |
| 验证 | 验证 API 和扫描竞争仅结案一次、通知失败回滚、两类领取超时的预留/名额/顺序差异、旧版确认拒绝及生效维护结案。见 CONS-01/02、AC-3.3-02/12/13、AC-3.5-02/04/07/14/17–22、AC-4.2-05/07。 |

### 3. PostgreSQL 与加锁顺序

| 项 | 约定 |
| --- | --- |
| 适用场景 | 开发、并发验收、演示及会改变占用、名额或交接的业务写入 |
| 具体约定 | 三种环境统一使用 PostgreSQL。耗时复检放在事务外，最终确认用 Django `atomic()` 和 PostgreSQL 行锁。依次锁 GPU、相关账号、预约或分配，同类按 ID 升序。新预约锁共同 GPU，涉及跨卡本人重叠时锁账号。最终复检发现遗漏对象时退出事务并按完整集合重来。受理序号由规则 2 的入口决定。并发验收为每个参与者建立独立连接和事务，使用同步点控制竞争时序。 |
| 依据 | ADR-002，NFR-001，故事 2.2、2.4、2.6、3.4、3.5 |
| 验证 | 用 `TransactionTestCase` 和实际 HTTP 并发分别核对锁边界和用户结果。记录独立连接、接收及确认顺序、受理序号和持久结果。CONS-01 跑 30 轮，CONS-02 三个分支各 15 轮。另测先到写入或复检慢、先到失败及本人跨卡重叠。 |

### 4. 时间存储、接口和截止裁决

| 项 | 约定 |
| --- | --- |
| 适用场景 | 预约及维护时段、预留、领取截止、超时与页面倒计时 |
| 具体约定 | Django 启用 `USE_TZ`，使用时区感知时间与 PostgreSQL `timestamptz` 保存时间点，以 UTC 对比。接口收发带偏移或 `Z` 的 ISO 8601 日期时间，页面统一显示 `Asia/Shanghai`。时段含开始、不含结束。有效接收、确认、截止和维护生效均由后端按持久状态与服务端时间裁决。返回服务端当前时间供倒计时展示。登记开始按 FR-010 的截止及宽限处理。预计结束、确认结束和实际释放分别保存。 |
| 依据 | PRD §1.2、FR-010、011、018、020、021，ADR-003。[PostgreSQL 时间类型](https://www.postgresql.org/docs/17/datatype-datetime.html) |
| 验证 | 测跨日、跨年、首尾相接、系统时区差异、客户端时钟偏差及恰好截止。暂停扫描，在生效维护起点后提交迟到的领取复检，核对无新增用卡记录。 |

### 7. 原请求编号和参数按账号隔离

| 项 | 约定 |
| --- | --- |
| 适用场景 | 提前预约和立即使用首次提交、刷新、重试及重新登录 |
| 具体约定 | 首次提交前持久保存请求编号与原参数。重试沿用原编号和参数。修改参数后生成新编号作为新申请，原申请仍可查询。客户端恢复信息按后端确认的账号隔离。服务端以认证账号与请求编号唯一约束绑定原参数，对同编号不同参数明确拒绝，成功结果与业务记录同事务提交。查询和重试核对归属，已成功返回原编号及原时段，处理中返回原状态，预约重试保留原受理序号。 |

### 8. 集中配置课程参数

### NFR-005 领取通知时效测试

1. 准备一张正在使用的 GPU 和一名符合空档及申请条件的在先等待者。用该等待者账号提前打开「我的等待」，保持页面在前台并启用自动更新。用另一账号登记释放。
2. 记录服务端确认「释放已登记且 GPU 已可交接」的时刻为起点。登记释放后仍有交接障碍时，以障碍解除、设备可交接的时刻起算。
3. 等待页面自动更新。以同一条领取通知同时显示 GPU、领取入口和截止时间的时刻为终点。整个过程保持页面打开，采用可对齐的服务端与浏览器计时记录，按释放事件和分配编号核对。
4. 有符合条件者时，端到端耗时须 ≤ 5 秒，含第 5 秒，自动更新、重试与渲染耗时均计入。未生成、未完整显示或超时均记录为未达标。无符合条件者时单列原因，无分配编号时按释放事件追溯。依据 PRD NFR-005、故事 3.3 及 END-01、END-03、QUEUE-04。结果待实测。
