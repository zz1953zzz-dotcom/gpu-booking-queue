# 课题组 GPU 预约与排队系统｜产品需求文档

## 1. 产品目标与范围

让组员判断所需时段有没有已知冲突，知道还需确认什么，再决定换卡、调整时段、预约或等待。系统根据已登记的设备资料、用卡安排、维护和交接信息给出判断依据。真实课题组的问题频率、协调耗时、使用效果与课程参数适用性均待验证。

- **组员**包括需要运行实验的学生和老师。以本人账号查卡、预约、等待、领取、登记开始、续用和释放。
- **GPU 管理员**维护设备资料、处理维护与故障、核实释放并组织调整确认。同一账号可以兼具两种身份。管理员本人用卡适用组员规则，优先级与其他组员一致。
- **第一版范围**限一个课题组。范围外包括访客、外部人员、跨组共享、成员管理页面、角色授撤页面、账号停用页面、实时剩余显存查询，以及在线暂停、中止或迁移服务器任务。服务器任务由人员在线下操作。组内可查看使用者姓名、GPU、使用时段、预计结束及更新时间。实验内容和训练数据无需填报或公开。

需求以 [定稿产品简报](product-brief.md) §4–§9 为依据。简报中的小林、小周和测试数据均为课程场景。D-01 至 D-05 和 Q-01 至 Q-03 的已确认规则见 §2，补充验收分支见 §5.1 和 §5.2。D-06 及其余后续设计事项见 §6。

### 1.1 关键使用场景

- **UJ-1 查卡与申请**。组员按最低显存和所需时段查卡，看清冲突和交接风险，再选卡预约或申请立即使用。提交时按最新记录复检。见简报 §2.3、§6.2.1–§6.2.2。
- **UJ-2 等待与交接**。组员在立即使用暂不可满足时主动入队，取得领取资格后在截止前领取。登记开始、续用及释放按记录状态和设备交接情况处理。见简报 §6.2.2–§6.2.4。
- **UJ-3 维护与协调**。管理员预览计划维护影响并取得所需确认，或先登记突发故障。受影响组员查看自己的原安排和原因。设备恢复且可交接后，系统按原序处理等待。见简报 §6.2.5。

### 1.2 术语与通用规则

| 术语 | 定义或规则 |
| --- | --- |
| 确认时段 | 已确认预约或用卡记录的起止时间。时段首尾相接不算重叠。所有日期时间统一按北京时间展示，跨日、跨月、跨年按完整时段判断。 |
| 预计结束 | 当前使用者填写的估计，与确认结束及释放登记分别记录。更新时间只在预计值填写或修改时更新。 |
| 设备可交接 | 以最新登记状态判断。前一位尚未登记释放、释放待核实、设备故障或维护等阻碍仍在时，禁止登记开始、立即使用或领取。 |
| 有效等待 | 已登记且处于「等待中」的记录，用于找卡人数和续用判断。「待领取」「领取处理中」「受影响」也占本人等待名额，各状态按对应流程处理。 |
| 待领取预留 | 分配给指定等待者的临时占用，有效期间参与同卡时段冲突检查。 |
| 领取窗口与处理时限 | 站内通知可见起算 10 分钟，系统须在截止前收到有效请求。收到后最多保留预留 30 秒供领取处理。 |

**FR-010 的宽限期与登记开始处理**

- **宽限期内受阻。** 原预约在登记窗口内仍有效时，前序未释放、故障或释放待核实等障碍导致无法交接，保留预约并说明原因，故障时标为「受影响」。全部障碍解除且 GPU 可以交接时，从可交接时刻重算 15 分钟，登记截止不晚于原预约结束。已经逾期的预约保持原结果，之后的故障及恢复均不恢复原预约。
- **登记截止与处理截止。** 按系统收到有效请求的时间判定是否按时提交，须早于登记截止。处理截止取「收到有效请求时刻加 30 秒」与「原预约结束」中较早者，须在处理截止前完成确认。登记截止到点时，自动逾期等待按时收到且仍在处理时限内的请求结案。在设备可交接且没有此类处理中请求时，按逾期处理并释放剩余时段。
- **取消与登记开始。** 按 FR-009，以先确认的操作为准。取消、登记开始与自动逾期的结案结果互斥。同一预约只有一个生效结果。
- **复检失败或处理超时。** 复检失败显示具体原因。达到处理截止仍未确认则结束该请求，迟到结果不能生效。两者均不生成用卡记录。原预约仍有效且登记窗口仍开放时可重新提交。窗口已过时，符合交接受阻保留条件的预约按该规则继续处理，其余按逾期释放剩余时段。若取消已生效，保留取消结果。
- **原预约到期。** 到原预约结束仍未确认时，结束处理资格并按未开始规则结案。交接障碍持续到原结束时，按实际原因记录未能开始，多重原因全部留痕。无适用的交接受阻情形时按普通逾期结案。
